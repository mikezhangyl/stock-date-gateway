## Job Lifecycle Requirements

Supported statuses:

- `accepted`
- `running`
- `completed`
- `completed_with_failures`
- `failed`
- `cancelled`

Required job metadata:

- `job_id`
- `status`
- requested symbol count
- completed symbol count
- failed symbol count
- row count
- started timestamp
- updated timestamp
- cache mode summary
- failure list with symbol/date scope and structured reason

Required behavior:

- job creation returns quickly and should not perform the full scan inline
- worker execution should use bounded internal sub-batches
- repeated create requests with the same semantic parameters should be idempotent
  or return an existing compatible job
- job rows should be retrievable even when status is `completed_with_failures`
- health endpoint must remain responsive while jobs are running
- no browser automation, proxy rotation, CAPTCHA bypass, or anti-detect work

## Error Semantics

Large scan errors should be data/job state, not unbounded HTTP hangs.

FNI can handle:

- immediate `accepted` job response
- `completed_with_failures` with partial rows and structured failures
- explicit `failed` job with structured failure reason
- HTTP `429` or structured queue-full response when the job queue is saturated

FNI should not need to handle:

- synchronous request hanging for minutes
- HTTP `504` for a normal large scan request when a job model is available
- empty success rows without job/failure explanation
